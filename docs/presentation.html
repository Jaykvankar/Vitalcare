Sem 5 · Information Security & Cryptography project

Vitalcare

An AI-based remote patient monitoring system that collects, analyses and stores health data, protected end to end with AES, SHA-512, RSA, Diffie–Hellman and DSA-family signatures.

Live demo: python demo.py · source: github.com/Jaykvankar/Vitalcare

The problem

Monitoring patients at home creates a privacy problem

  • Wearables send heart rate, SpO₂, blood pressure, temperature and breathing rate every few minutes.
  • That data crosses home Wi-Fi and the internet, and sits in a hospital database for years.
  • Clinicians cannot watch every number, so deterioration must be flagged automatically.

Threats

Eavesdropping, fake devices, replayed or altered readings, stolen databases, curious insiders, edited audit logs.

Goal

Collect securely, analyse with AI, store so that only the patient's own care team can ever read it, and prove who accessed what.
Architecture

From the sensor to the care team

Stack: FastAPI + SQLAlchemy (SQLite or PostgreSQL), React + TypeScript, Python cryptography library for the primitives. Protocols are our own.

Protocol 1

Sealing one reading on the device

  1. Device makes a fresh DH key pair e, E = gᵉ mod p (3072-bit).
  2. Shared secret with the server's public DH value → HKDF-SHA-512 → AES key.
  3. Vitals encrypted with AES-256-GCM; header (device, time, sequence) bound as associated data.
  4. Whole packet hashed with SHA-512; digest signed with the device's RSA-PSS key.
  5. Server: check signature → check time ±60 s and sequence is newer → decrypt.

What an attacker gets

Only E, a nonce, ciphertext, tag and signature. The DH secret e is thrown away, so recording traffic today cannot be decrypted later.

Protocol 2

Pairing a device, storing data

Pairing (one-time code)

  1. Clinician or admin creates a code (10 min, 5 tries) shown as text + QR.
  2. Device makes its own RSA-3072 key pair.
  3. Sends its public key + HMAC-SHA-512(code, key). The code never crosses the network.
  4. Server checks the HMAC and registers the key for that patient only.

Storage (envelope encryption)

  1. Each patient has their own AES-256 data key.
  2. That key is wrapped (AES-GCM) by a versioned master key kept outside the database.
  3. Master key rotation re-wraps data keys only.
  4. Erasure = destroy the patient's key (crypto-shredding); backups become unreadable too.
Protocol 3

Who can see what, and proof of it

Sign-in

Passwords hashed with PBKDF2-HMAC-SHA-512. Staff need a TOTP code (HMAC-SHA-512); one-time recovery codes. Rate limits and lockout.

Access rules

Clinicians see only assigned patients; patients only themselves; admins manage accounts but cannot read any vital sign. Patient can pause sharing at any time.

Privacy ledger

Every access appended with the SHA-512 of the previous row (unique, so no forks). Checkpoints signed with ECDSA P-384. Editing any row breaks the chain.
AI analysis

Three layers, explained in plain language

Clinical rules

Hard limits (e.g. SpO₂ below 92 %) give an immediate critical alert.

NEWS2

The UK early-warning score used in hospitals, from whatever vitals were measured.

ML model

Gradient boosting over 18 features (values, trends, change from the patient's own baseline). File pinned by SHA-512 so it cannot be swapped.
Partial readings: real sensors measure only some vitals. Missing values show as Not measured, never invented. Rules and NEWS2 use what is present; the model scores only complete readings.

Decision support only: every alert shows its reasons and is acknowledged by a clinician with an encrypted note.

Honest limits

What is not done yet

Limits

  • Bluetooth gateway decodes the standard health services and is tested byte-for-byte, but not on physical devices.
  • The AI is trained on a small open dataset (about 100 ICU deaths); NEWS2 is still better on MIMIC.
  • Master key can be sealed or come from an HSM/KMS; no HSM hardware was tested.
  • Not clinically certified; a research prototype.

Future work

  • Retrain on the full credentialed eICU / MIMIC-IV.
  • Certify specific Bluetooth devices; phone app as gateway.
  • HL7 FHIR feed from hospital bedside monitors.
  • SMS / push alerts, cloud key management service.
